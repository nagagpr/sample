Repo: C:\Work\edas-api-service. Reference implementation: portal-api (announcements), which works from OutSystems with a human Okta token.

GOAL
Make POST /v1/statements and GET /v1/statements/{id} authorize human callers the same way portal-api's announcements do, so OutSystems can call them. Today both return 403 for human tokens, because auth_service.can_access_resource (statements_router.py lines 171 and 386) requires the statements.read scope and a cpp_id claim, which human tokens don't have.

DECISIONS (already made, follow them)
1. Caller identity: port portal-api's get_user_context logic (user_context.py) into this repo. The email comes from sub, falling back to the email claim, plus the Internal flag. Keep today's JWT signature validation.
2. Human or machine: if the token has a valid email address, use the new database entitlement check. If not (machine tokens, where sub is usually a client ID), keep the existing statements.read scope and cpp_id claim check exactly as it is.
3. Entitlements for human callers, queried through RDSProxyService like the other services (DATABASE_PROXY_ENDPOINT, DATABASE_DB_NAME and DATABASE_DB_USER are already set on the Lambda):
   - Look up the user by email in mrd.user_profile. No active profile means 403.
   - Internal users can access all CPPs.
   - External users can access only the CPPs in their active assignments in mrd.user_external_cpp_role_assignment joined to mrd.client_program_participant, using the same joins as portal-api's GET_USER_SEARCH_QUERY.
   - For now, an active assignment for the CPP is enough. Add a setting STATEMENTS_REQUIRED_FUNCTION_CD, empty by default. When it's set, also require that rnt_function_cd in mrd.user_entitlement with access level R or W, checked the same way portal-api checks its function codes.
4. Email domain check: apply portal-api's EmailValidator the same way it does.
5. Location: build it in this repo, not in eas-api-common, as separate modules (for example auth/user_context.py and auth/entitlements.py) so it can move to eas-api-common later.
6. GET /v1/statements/{id}: check access against the CPP in the statement itself, which is the prefix of statement_id (DDM:B1FW in DDM:B1FW_4f73f38cc4e7_20251231_DDM_Monthly). Never check against a value the caller sends. Use the existing statement_id parsing code.
7. Status codes and error bodies: match portal-api.
